Background: Terminal-Bench 4.0 Leaderboard

Terminal-Bench 4.0 is a benchmark by Stanford / Harbor / Laude Institute that measures AI agents' ability to complete real-world software tasks in a terminal environment. 66 tasks across 7 categories (Software, Science, ML, Operations, Security, Hardware, Media), each graded pass/fail by an automated verifier. An agent runs inside a Docker container, interacts with the terminal, writes code, and must pass all tests to count as solved.

Resolution Rate = fraction of 66 tasks the agent fully solved (all verifier tests pass). No partial credit — a task is either solved (1) or not (0).

Key insight from per-task data:

  1. Same task, different outcomes. vf2-speedup-networkx passed 1/2 runs — the same model on the same task sometimes succeeds, sometimes fails. This is agent loop variance, not model capability ceiling.
  2. Cost varies wildly per task. photonic-waveguide-routing cost only $2 (agent gave up in 55 min), while sglang-qwen-burst cost $8,065 (agent ran 1h 41m burning tokens). Both failed.
  3. Failed tasks still burn money. 14 tasks had 0% pass rate but Opus 5 spent real money trying — $24,898 total across just these failed attempts. A router that recognizes "this isn't working" earlier could cut losses.
  4. Cannot pre-judge model capability. Different models have different strengths. A task that Opus 5 fails might be solvable by GLM-5.3 or GPT-5.6 Luna — we just don't have that cross-model per-task data yet.

Goal

Can aware-gateway's task-router reduce total LLM cost without sacrificing response quality, by choosing cheaper models when they're "good enough" for the current turn?

We simulated a harbor terminus_2 agent loop — the same pattern used in Terminal-Bench 4.0 — for 5 generic software engineering tasks. Each task runs 5 turns with growing conversation history (prompt tokens increase from ~250 to ~700 as the agent accumulates context).

Agent Loop (5 turns per task)

Turn 1: Understand — "Read the task, summarize what needs to be done"
Turn 2: Plan     — "Create a step-by-step implementation plan"
Turn 3: Code     — "Implement step 1, write the core code"
Turn 4: Review   — "You ran the code, got this output: ... Analyze"
Turn 5: Fix      — "Fix issues and write the final version"

Each turn appends the assistant's response to the conversation history, so prompt tokens grow naturally (~250 → ~700).

Quality Scoring

Each response is scored by counting how many task-specific keywords appear (e.g., "script", "html", "sanitize" for html-js-filter). Higher = more relevant response. This is a proxy for "did the model understand and address the task" — not a full verifier pass.

Key Findings

1. Smart-router chose GLM-5.3-flash for all 5 tasks

The Qwen3.8-27B decision model analyzed each request and determined that all 5 tasks (≤5h expert time) could be handled by the cheapest model. Cost matched ultra-cheap exactly: $0.0039 total vs $0.0732 for all-mid (GLM-5.3) — a 95% cost reduction without sacrificing quality.

2. Smart-router quality matched or beat ultra-cheap

On interleaved-vigenere, smart-router scored 4.0 vs ultra-cheap's 2.4 — despite using the same model (GLM-5.3-flash). The quality difference comes from LLM generation randomness (temperature=0 is not fully deterministic across API calls). On other tasks, scores were within ±1 of ultra-cheap.

3. More expensive ≠ better quality

GLM-5.3 ($1.40/$4.40, TB #3) scored 1.8 on interleaved-vigenere — worse than GLM-5.3-flash ($0.07/$0.25) at 2.4. GPT-5.6 Luna ($0.20/$1.20, TB #8) also underperformed flash on most tasks. For ≤5h tasks, the cheapest model is optimal.

4. Decision model overhead is negligible

Qwen3.8-27B (vLLM on L40S) with thinking disabled makes routing decisions in ~4s. With 5-minute cache TTL, repeated similar prompts skip the decision call entirely. Decision cost is tracked separately in traces (step=router-decision) for billing.

5. Run 1 vs Run 2 comparison

Run 1 used the outdated GPT-4o as "expensive" baseline and a hardcoded turn-based upgrade strategy for gateway-router (flash for turns 1-2, expensive for turns 3-5). Run 2 replaced GPT-4o with Terminal-Bench 4.0 leaderboard models and let the smart-router's LLM make per-call decisions autonomously. The smart-router's autonomous choice (always flash) was simpler and more cost-effective than the hardcoded upgrade strategy.

Implications for aware-gateway

Architecture validated

  1. Smart-router (LLM-based) + task-router (rule-based) = chain-of-responsibility. Smart-router runs at priority 50, task-router at 100. If smart-router's LLM decision fails, it returns Skip and task-router handles it. Zero coupling.
  2. Decision model: Qwen3.8-27B on vLLM (L40S). Thinking disabled via chat_template_kwargs.enable_thinking: false for ~4s decisions instead of ~10s. DiffusionGemma-26B available as alternative (higher throughput but ~9s TTFT — not suitable for routing).
  3. Decision caching. Same prompt prefix + model menu = cached decision for 5 minutes. Eliminates redundant LLM calls for similar requests.
  4. Decision cost tracked separately. Each routing call is recorded as step=router-decision in traces, enabling independent billing analysis.
  5. Model pinning preserved. Clients can bypass smart-router by sending a known model ID. Only model="auto" triggers LLM-based routing.

Next steps

  1. Test with harder tasks (≥10h expert). All 5 benchmark tasks were ≤5h — the decision model correctly chose flash for all. Harder tasks should trigger upgrades to GLM-5.3 or GPT-5.6 Sol.
  2. Add all-premium baseline. Compare smart-router against GPT-5.6 Sol ($2/$10) to measure savings vs a top-tier model.
  3. Budget cap per trial. Stop upgrading when cumulative cost exceeds a threshold — let the router downgrade to cheaper models as the budget depletes.
  4. Context-aware routing. Feed the decision model information about previous turns' model choices and quality, so it can adapt as the agent progresses.
  5. Integrate with harbor terminal-bench. Set OPENAI_BASE_URL=http://aware-gateway:12026/v1, pass trial/step names via extra_headers, run real agent trials.
