从 aware-gateway 到 Smart Router：一次省钱路由实验的完整故事

这篇 blog 从头讲清楚：为什么要做 aware-gateway，网关怎么把模型调用、路由、成本和 trace 串起来， smart-router 为什么有可能省钱，以及我们怎样从 V3 的粗实验一路收敛到 V4 的可解释 benchmark。 它不是 leaderboard 提交，也不是最终论文结论；它是一份工程实验复盘，重点是哪些数据能信， 哪些只是噪声，以及下一步该怎么把 smart-router 做成可泛化的决策系统。

核心结论很短：smart-router 的价值真实存在，但不是“便宜模型越多越好”。 在 shadow-relay 上，它可以稳定通过，并且 warm-start / critical-path budget 这类策略能把成本压到一个可接受区间。但在 vpp-loss-divergence 上，本地 reduced-time 协议暴露出长路径和 provider tail 风险，继续把它作为主要 prompt 研究任务并不划算。

先把来龙去脉讲清楚

我们一开始不是为了“又造一个代理服务器”。真正的问题是：今天的 agent 做一个任务会调用模型几十次， 每次都用最强模型很贵；每次都用便宜模型又可能在关键步骤翻车。aware-gateway 的作用，就是站在 agent 和模型供应商之间，把每一次调用都变成可路由、可计费、可追踪、可复盘的数据。

背景
模型调用需要一个控制面

agent 只管发 OpenAI-compatible 请求；网关负责选择实际模型、转发请求、记录成本和结果。

假设
不是每一步都需要 Opus

读文件、跑测试、做局部验证可能适合 flash；关键推理、复杂修复和最终收敛更适合 Opus。

实验
用 benchmark 检验质量

Terminal-Bench/Harbor 给出任务、环境和 verifier。我们看 reward、cost、调用次数和路由决策。

结论
路由要像状态机

只告诉 router “省钱”不够。它还要知道当前处于探索、关键假设、恢复、验证还是收尾阶段。

aware-gateway 的设计：它站在哪里

aware-gateway 是一个 OpenAI-compatible reverse proxy。外部 agent 仍然像平时一样调用 /v1/chat/completions；区别是，请求先经过网关。网关可以在不改 agent 主逻辑的情况下， 增加限流、审计、OpenTelemetry、模型池、重试、fallback，以及本次实验最关键的 smart-router。

01
Agent

发起一次模型调用。它可以只说 model=auto，不用提前知道该用 flash 还是 Opus。

02
Core Handler

读取请求、挂载 session metadata，按插件优先级执行 middleware 和 router。

03
Smart Router

用决策模型读取当前上下文、最近几轮路由记忆、模型成本和能力，返回要使用的模型。

04
Proxy + Pool

把请求转发到 OpenRouter 或其他后端；按模型选择对应 endpoint，并处理 retry / fallback。

05
Trace + Audit

记录 routed model、status、token、provider cost、decision reason，之后能做 replay 和可视化。

插件化，而不是写死逻辑

router、audit、metrics、middleware 都是插件。smart-router 跑在 task-router 前面；它不决策时，规则路由还能兜底。

session 级归因

每个 benchmark trial 都需要一个稳定 trace key。否则 agent 轨迹、gateway trace 和 provider cost 对不上，实验会失真。

成本是一等指标

网关同时记录 agent call 和 router decision call。省钱实验不能只算完成任务的模型调用，也要算“派单员”自己的成本。

决策可回放

每次 smart-router 的输入上下文和输出理由都会保存。这样可以冻结 agent 轨迹，只改提示词，离线比较不同 router prompt。

Smart Router 到底在做什么

可以把 smart-router 想成一个“模型调度员”。每当 agent 要走下一步，它先看这一步像不像关键步骤： 是在读信息、机械搜索、跑便宜验证，还是在做高风险推理和收尾修复。然后它从菜单里选一个模型。 当前 V4 菜单故意只保留两档：z-ai/glm-5.3-flash 和 anthropic/claude-opus-5。这样结果比较干净：不是三四个模型混在一起，而是明确观察 “便宜档”和“强模型档”如何分工。

组件 当前选择 为什么这样设计
决策模型 openai/gpt-5.6-sol 替代已移除的 Qwen3-27B endpoint，用稳定的外部模型产生结构化路由决策。
候选模型 glm-5.3-flash / claude-opus-5 只保留便宜和最强两档，避免中间模型把实验解释搅混。
Warm-start 任务前 5 次 agent 调用强制 Opus 先让强模型建立方向和上下文，再观察后续自由路由是否能省钱。
最近记忆 最近 5 轮决策摘要 让 router 知道前面是否已经升级过、是否连续恢复失败、是否该降级做便宜验证。

实验问题：我们到底想证明什么

这轮设计的核心不是“smart-router 看起来很聪明”，而是更朴素的 GQM 结构： 先定义目标，再把目标拆成问题，最后只收集能回答这些问题的指标。

Goal

验证 smart-router 能否在不明显降低任务完成质量的前提下，降低每个 solved trial 的成本。

Questions

它能做对吗？比公开 Opus 参照贵还是便宜？它什么时候选 flash，什么时候选 Opus？失败是路由问题还是环境/provider 问题？

Metrics

reward、cost per solved、agent calls、decision calls、模型选择比例、provider 5xx、trace 覆盖率。

统计口径

数据来自两个位置：仓库内 artifacts/ 的 V3 记录，以及 /mnt/data2/aware-gateway-runs/ 的 V4 真实 run / replay / HTML 报告。 统计时按逻辑 trial 去重；同一条 canary 既保存为 harbor-canary-analysis.csv 又保存为 experiment-id 文件时，只算一次。

成本口径要分层看：V3 与部分早期 V4 使用 trajectory 重算成本，只能当趋势； V4 主实验及之后的 live pilot 使用 gateway_trace_upstream_cost， agent cost 和 decision cost 都能归因到 session，因此可信度更高。

实验是怎么一步步收敛的

这轮实验不是一开始就长成现在这样。我们先试了更大的矩阵，发现真实 bottleneck 不是“能不能启动 benchmark”， 而是长任务成本、provider tail、trace 归因和失败解释。后来才把设计收窄成：少量代表性任务、 只比较 smart-router 和公开强模型参照，把预算集中花在真正能回答问题的地方。

阶段 当时的想法 发现的问题 后来的调整
V2 / V3 用 5 个任务 × 3 个策略 × 多次重复，直接比较 all-flash、all-premium、smart-router。 矩阵太大；trace/session 归因一旦不稳，成本和质量就对不上；部分任务单条就会拖很久。 先修 gateway trace 归因，再降低实验规模。
V4 主设计 借公开 leaderboard 做外部参照，只在本地跑必要的 smart-router 对照。 公开榜单够看 aggregate，但看不到每一步 run log 和 router 决策理由。 本地只跑 smart-router 相关策略，同时保留每次 decision context。
任务选择 原本想覆盖 5 个任务。 代表性不等于数量越多越好；长任务会把预算烧在 provider tail 和 agent 搜索路径上。 收敛到 shadow-relay 和 vpp-loss-divergence，前者做主研究台架，后者做压力边界。
策略选择 考虑继续跑 all-flash。 all-flash 既慢又很难保证质量，而且公开榜单已能提供强模型参照；本实验真正要检验的是 smart-route。 放弃 all-flash，把预算转向 smart-router、warm-start 和 prompt 变体。
Prompt 研究 先把“成本”直接写进提示词。 只写成本会让离线 replay 更偏 flash，但 live run 仍可能保守；有时还会牺牲泛化。 转向 critical-path 和 history-aware：让 router 根据任务阶段、最近决策和恢复状态做选择。

replay 告诉我们“可能怎么选”，live run 告诉我们“这样选会不会改变后续轨迹并影响质量”。 二者必须配合看。history-aware-v1 离线看起来非常省 Opus， 真实 shadow-relay run 也通过了，但成本仍有 $4.45，因为少数 Opus 大上下文调用很贵。

目前判断

  1. 继续用 shadow-relay 做 prompt 研究。 它足够难，有多阶段推理、验证和恢复；又足够短，不会每次吞掉几个小时。
  2. 暂时不要把 vpp-loss-divergence 当主任务。 它适合作为压力测试，不适合快速迭代路由提示词。
  3. history-aware 是正确方向。 最近 5 轮决策摘要让 router 有“路线感”，能看到刚才为什么升 Opus、是否已经连续 premium stalled。
  4. 下一步不是简单调一句 prompt。 应该把路由决策拆成状态机：orientation、mechanical probe、critical hypothesis、recovery、 finalization，并给连续 recovery 设置预算、冷却和便宜验证要求。

下一轮建议

下一轮用两个短任务做小矩阵：shadow-relay 作为正样例， 再选一个比 vpp-loss-divergence 短、但仍有 hidden/generalization 风险的任务作为泛化样例。 每个 prompt 先跑离线 replay，再只把最有希望的 1 到 2 个 prompt 做真实 Harbor run。 

1. 冻结已有 trajectory，继续离线 replay：
   - history-aware-v1
   - history-aware + recovery budget
   - history-aware + cheap validation before second Opus

2. 真实 Harbor pilot：
   - shadow-relay / best prompt / 2 attempts
   - short generalization task / best prompt / 1 attempt

3. 成功标准：
   - reward 不下降
   - cost per solved 接近或低于 $3-$4
   - Flash 不是盲目增多，而是集中在 orientation / mechanical probe / bounded validation
