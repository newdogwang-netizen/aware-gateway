aware-gateway 设计案例：让 AI Agent 更会花模型预算

这是一篇给外部开发者看的工程 case study。我们把一个 OpenAI-compatible 网关放在 agent 和模型供应商之间， 让每一次模型调用都可以被路由、计费、追踪和复盘。然后用 Terminal-Bench 检验一个具体假设： 能不能把简单步骤交给便宜模型，把关键步骤交给强模型，在质量不明显下降的前提下降低成本。

结论先说清楚：smart-router 有价值，但它不是一个简单的“便宜优先”开关。 好的 router 要把强模型调用集中到关键假设、恢复和最终收敛阶段；把便宜模型放在读取上下文、 机械探查和 bounded validation 上。否则，它要么过度保守、成本降不下来，要么盲目省钱、质量掉下来。

1. 为什么需要一个 AI Gateway

Coding agent 做一个任务时，通常不是一次模型调用结束。它会读文件、搜索线索、改代码、跑测试、 解释失败、再继续修。一个 trial 里几十次模型调用很常见，而这些调用的风险和价值并不一样。

如果 agent 直接绑死一个模型，就只剩两个粗暴选择：全程用最强模型，质量稳但贵；全程用便宜模型， 成本低但容易在关键步骤错。aware-gateway 的目标是把“模型选择”从 agent 里抽出来，变成一个可观察、 可替换、可实验的控制层。

01

Agent

继续发普通 OpenAI-compatible 请求。它可以只写 model=auto。

02

Core Handler

读取请求，挂载 session metadata，并按优先级执行插件。

03

Smart Router

根据当前上下文、最近历史、模型价格和能力，决定本次调用走哪个模型。

04

Proxy + Pool

把请求发到 OpenRouter 或其他后端，并处理 endpoint 选择、retry 和 fallback。

05

Trace + Audit

记录 routed model、token、provider cost、status 和 decision reason。

为什么放在网关层，而不是 agent 里？

这样可以不改 agent 主逻辑就切换路由策略。相同的 benchmark scaffold 可以跑 all-premium、smart-router、warmstart 或新 prompt，差异都集中在 gateway 层。

为什么 trace 是核心功能？

省钱实验最怕“感觉便宜”。必须把每个 trial 的 agent trajectory、gateway trace、provider cost 和 verifier reward 对上，才知道 cost per solved 是否真的下降。

2. Smart Router 的策略空间

当前实验故意把菜单收窄到两档模型：z-ai/glm-5.3-flash 和 anthropic/claude-opus-5。这让实验更容易解释：每次决策基本都在回答 “这一步值不值得花 Opus 的钱”。

Component Current choice Reason
Decision model openai/gpt-5.6-sol 替代已移除的 Qwen3-27B endpoint，用稳定外部模型产生结构化路由决策。
Cheap model z-ai/glm-5.3-flash 工作先验：智能水平约为 Opus 的 75%，但输入/输出单价约低 71x/100x。
Premium model anthropic/claude-opus-5 作为质量锚点，用在高风险推理、恢复和最终收敛。
Warm-start 前 5 次 agent 调用强制 Opus 先用强模型建立方向和任务状态，再让 router 自由选择。
Recent memory 最近 5 轮决策摘要 让 router 知道刚才是否已经升级过、是否连续恢复失败、是否该降级做便宜验证。

3. 实验设计：少跑，但对照点要清楚

最早的设计想跑大矩阵：多个任务、all-flash、all-premium、smart-router、多次重复。 真实执行后我们缩小范围，因为外部开发者真正关心的不是“跑了多少行表格”，而是 smart-router 相对强模型参照是否有可解释的质量/成本信号。

Goal

在 verifier reward 不明显下降的前提下，降低每个 solved trial 的成本。

Questions

它能做对吗？成本比公开 Opus 参照如何？什么时候选 flash，什么时候选 Opus？失败是路由问题还是环境/provider 问题？

Metrics

reward、cost per solved、agent calls、decision calls、模型选择比例、provider 5xx、trace 覆盖率。

Design decision Final scope Why

4. 核心结果：把对照点合在一张表里

这张表是本文最重要的证据。它不是 run log，而是回答一个产品化问题： 如果把 aware-gateway 接到 agent 前面，smart-router 在可解任务上能不能保持质量，成本是否进入可接受区间？

Question Evidence Developer takeaway
shadow-relay 是否适合作主任务？ 公开 Opus 5 参照 5/5 通过，成本 $1.58-$2.94，平均约 $2.16；本地 V4 smart-router + warmstart 主矩阵 4/4 通过。 适合。它足够短，又覆盖真实 agent 的探索、推理、验证和恢复步骤。
普通 smart-router 表现如何？ shadow-relay 上 2/2 通过，平均成本约 $4.56，平均约 20.5 次 agent 调用。 质量信号成立，但成本仍高于公开 Opus 参照。单靠“让 LLM 自己选模型”还不够。
warm-start 是否有帮助？ 前 5 次调用强制 Opus 后，shadow-relay 2/2 通过，平均成本约 $3.39。 有帮助。先用强模型建立方向，再让 router 降级，通常比完全自由路由更稳。
目前最好的 live 策略是什么？ critical-path-budget-v2 在 shadow-relay 上 1/1 通过，成本 $2.68，14 次 agent 调用。 这是最有希望的方向：Opus 用在关键路径，flash 用在机械探查和验证。
vpp-loss-divergence 如何解释？ 公开 Opus 5 参照 5/5，平均约 $12.11；但本地 reduced-time 下 all-premium / smart-router / warmstart 共 0/4。 先当压力测试，不当主优化任务。这里混入了长路径、provider 5xx、timeout 和上下文膨胀。

6. Prompt 变体真正说明了什么

prompt 变体的价值不是给每个版本排榜，而是暴露 router 的决策机制。到目前为止，最重要的发现是： 成本信息必要但不充分；能力先验太粗；关键路径和最近历史比单轮分类更有用。

Router prompt idea Live signal What it teaches
Cost-aware shadow-relay 通过，但成本 $6.26，Flash 2 / Opus 25。 把价格写进 prompt 会提醒 router，但不会自动形成好策略。模型为了安全仍会大量选 Opus。
Flash = Opus 75% intelligence shadow-relay 通过，但成本 $6.87，Flash 5 / Opus 22。 能力先验有用，但仍然太粗。router 需要知道任务阶段，而不是只知道两个模型强弱比例。
Critical-path budget shadow-relay 通过，成本 $2.68，14 次 agent 调用。 最好的 live 信号：把 Opus 留给关键假设和收敛，把 flash 用于机械探查和便宜验证。
History-aware shadow-relay 通过，Flash 14 / Opus 8，成本 $4.45。 最近 5 轮决策摘要让 router 有“路线感”。即使成本不是最低，它给出了更可泛化的控制结构。

7. 为什么 Decision Replay 很关键

真实 benchmark run 很贵。decision replay 的做法是冻结已有 agent 轨迹，只替换 router prompt， 观察同一段上下文下新 prompt 会怎么选模型。这样可以先便宜地筛选路由策略，再把最有希望的版本拿去跑真实 Harbor trial。

Replay family Observed allocation Interpretation
Cost-aware 482 条决策上下文；有效 481；Flash 253 / Opus 228。 离线会更愿意用 flash，但真实 run 仍保守，说明目标还不够结构化。
Critical-path budget 20 条 smoke replay；Flash 10 / Opus 10。 小样本里开始把 Opus 集中到关键路径，是 live pilot 成本下降的前奏。
History-aware 482 条决策上下文；有效 480；Flash 364 / Opus 116。 最强离线信号。最近历史比单轮上下文更能改变 router 行为。

replay 告诉我们“同样的上下文下可能怎么选”；live run 告诉我们“这样选会不会改变后续轨迹并影响质量”。 二者必须一起看。只看 replay 容易过度乐观，只看 live run 又太贵、太慢。

8. 给 LLM 网关开发者的工程结论

  1. 先修 trace，再谈 benchmark。 如果 session id、agent trajectory、gateway trace、provider cost 对不上，后面的成本结论都不可靠。
  2. 不要用 all-flash 证明 smart-router。 all-flash 是成本下界，不是好产品策略。真正的问题是何时值得升级到强模型。
  3. 把 router 当控制器，不是分类器。 单轮 prompt classification 太浅。更好的 router 需要任务阶段、最近决策、恢复预算和冷却规则。
  4. 优化目标是 cost per solved。 便宜调用变多本身没有价值；只有 verifier reward 不下降，成本下降才有意义。

9. 下一步：从 prompt 调参走向状态化路由

下一轮不应该继续做创可贴式 prompt 微调。更好的方向是把 smart-router 明确建成一个小型状态机： orientation、mechanical_probe、critical_hypothesis、 recovery、finalization。每个状态有不同的默认模型、升级条件和预算上限。 

1. 离线 replay：
   - 冻结已有 decision contexts
   - 比较 history-aware、recovery-budget、cheap-validation-before-second-Opus

2. 真实 Harbor pilot：
   - shadow-relay / best stateful router / 2 attempts
   - one short generalization task / best stateful router / 1 attempt

3. 成功标准：
   - reward 不下降
   - cost per solved 接近或低于 $3-$4
   - Flash 集中在 orientation / mechanical probe / bounded validation
   - Opus 集中在 critical hypothesis / finalization / high-risk recovery

Reproducibility: 本文有意只保留支撑 developer-facing 论证的证据。历史 V3/canary runs、 原始 run logs 和生成的 lab 页面仍可用于审计，但不作为 headline evidence。公开参照来自 Harbor leaderboard 的 task-level Opus 5 明细；本地成本优先来自 gateway trace 的 upstream_inference_cost。
