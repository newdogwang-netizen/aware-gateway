从单次 LLM Router 到 Agent 轨迹控制

LLM routing 最容易讲清楚的目标其实只有一句话： 在质量不明显下降的前提下，把模型成本降下来。 经典单次路由可以把这件事讲得很干净：强模型、弱模型、一个阈值，然后画出成本和质量的取舍。 aware-gateway 要解决的是同一个问题的 agent 版本：成本不发生在一次请求上，而发生在一整条任务轨迹上。

这篇报告只回答一个问题：aware-gateway 相比单次请求路由，多做了什么， 以及现有数据能支持到哪一步。它不把内部状态机当卖点；状态机只是为了把成本-质量评估做准。

先把评估方式说清楚

单次请求路由可以用一个简单曲线表达：横轴是强模型调用比例或成本，纵轴是质量。 阈值越保守，强模型用得越多，质量更稳但更贵；阈值越激进，成本下降，但质量可能掉。

Agent 任务也应该这么评估，只是横轴不能只看单次请求。一个 coding agent 会在同一任务里连续调用模型、 跑命令、读文件、写产物、触发隐藏测试。真正要比较的是整条轨迹。

一条 agent 请求实际怎么走

上面是本轮请求，下面是结果回流。关键点是：router 不是只选模型，还会写入本轮行动要求。

1. Agent
发起下一轮模型请求

可能是读文件、分析、写代码、修测试，或者准备交付。

→
2. Gateway
先看确定性状态

如果只是读文件，用便宜模型；如果重复失败或接近交付，升级。

→
3. Router
输出 route action

决定模型、输出预算、timeout，以及本轮应该探索、执行还是恢复。

→
4. Upstream
Flash 或 Opus 执行

模型返回后，agent 继续跑工具、改文件、跑测试或生成交付物。

结果怎么回到下一轮
gateway 把工具、文件、测试和 verifier 结果投影成 Episode state。下一轮路由会看到这些状态： 已经有进展就压缩探索，连续失败就恢复，已有交付证据才允许完成。
tool_call file_written test_passed analysis_progress verifier_result

成本-质量怎么读

这不是看某一次调用便宜不便宜，而是看一整条任务最终有没有做成，以及做成花了多少钱。

便宜但冒险

更多 Flash，成本低，但复杂推理和失败恢复可能不够。

按状态切换

读文件和简单执行便宜跑，关键判断和恢复再升级。

稳但昂贵

更多 Opus，质量更稳，但如果每轮都用就失去路由价值。

指标 单次请求路由口径 Agent 场景下的 aware-gateway 口径
质量 benchmark score 或强模型性能保留率。 hidden verifier reward、solved rate、最终交付是否通过。
成本 一次回答使用强/弱模型带来的成本。 整条轨迹成本：agent 调用、decision 调用、失败和 stop 前已花掉的钱。
调节旋钮 路由阈值，控制强模型调用比例。 状态阈值和 route action：什么时候 cheap probe、什么时候 premium recover、什么时候 stop。
曲线 不同阈值下的成本-质量边界。 不同策略、不同任务、不同 stop gate 下的完成成本边界。

单次请求路由和我们到底差在哪

经典单次请求路由的核心链路可以简化成：看一次请求，估计强模型胜率，和阈值比较，决定走强模型还是弱模型。 这个问题足够清楚，所以很容易用一张曲线讲明白。 

request -> estimate strong_model_win_rate
        -> compare with threshold
      -> choose strong_model or weak_model

aware-gateway 当前要处理的是 agent 轨迹。某一轮请求看起来可能只是“读文件”，但它处在不同阶段时含义完全不同： 早期读文件是探索；已经有候选答案后还在读文件，可能是在拖延交付；测试失败后再读文件，可能是在恢复。 所以单看当前请求不够，必须看它前面发生过什么。 

agent turn -> gateway route -> model call -> tool/file/test/verifier events
           -> episode state -> next route action -> outcome

单次请求路由解决的是请求选择

强/弱模型二选一，重点是阈值校准和评估曲线。它适合普通问答或单轮服务里的模型替换。

aware-gateway 解决的是轨迹控制

一次任务里有几十次调用，router 必须知道是否有真实进展，并把下一轮变成更小、更准、或及时停止。

当前架构

smart-router 现在有三层。第一层是本地 safe-control，处理确定性场景；第二层是 prompt router，处理模糊判断； 第三层是 Episode 状态，把上一次选择和后续结果关联起来，影响下一次路由。

层 做什么 例子
Safe-control 不用问 judge，直接做高置信路由。 读文件走 Flash；重复错误或 verifier 失败走 Opus；超成本且无交付证据则本地 stop。
Prompt router 模糊场景仍用语义判断。 早期协议建模、复杂恢复、隐藏测试 gap、关键路径推理。
Episode state 记录同一任务线的历史和结果。 是否有文件写入、是否有测试通过、是否只是探索、是否连续截断、是否已经接近交付。

路由动作比模型名更重要

只说“选 Flash 还是 Opus”不够。一次路由还应该说明这轮要做什么、给多少输出空间、是否允许继续探索。 所以我们把 decision 扩成了 route action。

Action 意思 通常模型
cheap_probe 读文件、搜索、看日志、做小范围事实收集。 Flash
cheap_execute 已知方向下的执行、格式化、简单验证或交付写入。 Flash
premium_reason 早期建模、协议推理、关键路径判断。 Opus
premium_recover 假设被反证、测试失败、卡住后换方向。 Opus
freeze_or_replan 长时间探索无进展时，停止扩大预算，先重规划。 Opus，短预算
hypothesis_apply replan 已经形成假设后，下一轮只能应用、验证或放弃这条假设。 Flash 或按状态升级
completion_guardrail 最终完成确认必须看交付证据，不能只看模型说“完成了”。 Opus

这一轮真正改动了什么

旧版本已经能 stop 坏轨迹，但还不知道“某条分析是否已经足够交付”。这轮的关键是把中间进展也变成事件， 让 router 不再只看到 length、cost 和错误。

信号 为什么加 下一轮怎么用
analysis_progress agent 已经解出关键事实或候选答案，但还没写入交付。 下一轮走 cheap_execute，要求把事实转成命令、验证或交付。
replan_hypothesis replan 之后必须知道新假设是什么。 下一轮走 hypothesis_apply，验证、实现或放弃这条假设。
delivery_candidate 已经有中间产物，但迟迟不写最终输出。 提醒一次 cheap delivery；多次不落地再 premium recover。
execution_stall shell/heredoc/交互式命令卡住，继续让模型续写没有意义。 要求恢复一个短的非交互命令或直接交付。

现在能接受什么，不能接受什么

可以接受

  • safe-control 作为子里程碑完成。
  • route action 能控制模型、预算、timeout 和必要的 agent instruction。
  • Episode state 能把 outcome 带回下一轮路由。
  • shadow-relay 上 V2 screening 通过，成本优于历史成功样本。

还不能接受

  • 不能说策略已经泛化。当前只有一个代表性任务的单次成功。
  • analysis_progress 是 inferred 信号，需要更多任务验证误报。
  • Harbor 仍靠 artifact watcher，native tool event hook 还没接到 agent runtime。
  • 还没有画出多任务成本-质量边界。

下一步怎么按成本-质量曲线评估

下一步不应该继续围绕 shadow-relay 调阈值。应该把它变成一组可比较曲线： 不同策略、不同任务、不同强模型使用比例下，solved rate 和 cost per success 怎么变。

要补的数据 做法
任务多样性 保留 shadow-relay 作为协议/逆向任务，再选一个短数据或算法任务做 holdout。
策略曲线 不是只跑一个配置，而是扫几档：更省钱、更均衡、更保守。
质量口径 主指标用 reward / solved rate；辅助看 hidden verifier 前是否有交付证据。
成本口径 用 cost per attempt 和 cost per success，失败和 stop 前成本都算进去。
验收门槛 screening 只需要 1 次；acceptance 至少每任务 3 次，不用单次运气关 Issue。 
目标曲线：
quality = solved rate / verifier reward
cost = total trajectory cost
control = premium share + decision calls + no-progress loops

接受策略：
同等质量下更低 cost_per_success
或同等成本下更高 solved rate

一句话总结

更清楚的评估方式应该是：先把路由问题讲成成本-质量曲线，再谈模型怎么选。 aware-gateway 当前的差异是评估单位变了：不是一次请求，而是一整条 agent 轨迹。 V2 的价值不在于多几个状态名，而在于它开始把“这轮选择之后到底有没有推进任务”变成可记录、可 replay、可验收的数据。
