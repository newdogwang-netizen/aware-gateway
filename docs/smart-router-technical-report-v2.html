当前最准确的项目状态是：状态化控制层已经在一个代表性任务上跑通闭环。 它证明了网关可以把 trace、tool event、delivery 和 verifier 反馈接进下一轮路由； 它还没有证明跨任务泛化，也没有完成 native live tool event hook 和离线策略演进。

原问题

第一阶段的 smart-router 是一个 prompt router：每次请求进来，先把上下文压缩成一个小 prompt， 让 decision model 在 Flash 和 Opus 之间选一个。这个设计能工作，但它有三个硬伤。

每轮都有 judge 税

文件读取、搜索、格式化输出这类低风险动作也要付一次 decision model 成本和延迟。

没有任务线记忆

router 只看当前请求，很难知道上一轮模型选择是否真的产生了文件、测试或 verifier 进展。

成本按轨迹发生

便宜模型如果把 agent 带进十几轮无效探索，总成本不一定低；强模型如果只用在关键点，反而可能更省。

网关层怎么改

这次没有让 aware-gateway 替 agent 做计划。它只做路由控制：根据已经观察到的证据，判断下一次调用最低需要哪档能力， 并把这次选择、预算和后续 outcome 写回 trace。控制粒度从 “model label” 扩展到 “route action”。

请求路径

smart-router 先走高置信本地控制；不命中时才调用 semantic decision model。

核心抽象

V2 的核心不是“多加几条规则”，而是把路由变成一个可审计的控制回路。每一轮路由都能回答： 它看到哪些状态、选择了哪个动作、动作之后是否真的推进了任务。

抽象 现在的实现 为什么重要
Episode 用 X-Episode-ID、X-Session-ID、X-Trial-Name 解析当前任务线，并维护最小 session stack。 router 不再只看当前请求，而是知道同一条任务线之前发生过什么。
Event 接收或抽取 llm_call、tool_call、file_written、test_run、verifier_result 等事件。 把“模型说了什么”之外的事实纳入路由，例如是否写了交付文件、测试是否真的过了。
State reducer 维护 cost、tokens、progress tier、route outcome、length pressure、failure frontier、completion readiness。 把原始 trace 归约成下一轮决策可用的紧凑状态。
Route Action cheap_probe、cheap_execute、hypothesis_apply、premium_reason、premium_recover、freeze_or_replan、completion_guardrail。 一次路由不只是选模型，还要选预算、timeout 和必要的 agent instruction。
Outcome 把路由后的文件、测试、verifier、no-progress 和 execution-stall 反馈关联回上一轮 route。 后续可以判断某类策略是在推进任务，还是只是制造更多调用。

控制回路

Route -> Event -> State -> Next Action

这个回路是 RSI R1 的主要交付：真实运行数据进入状态，状态反过来约束下一次路由。

V2 新增的状态信号

旧版本只知道模型响应是否截断、调用是否报错。V2 把“正在推进”拆得更细，尤其区分 activity 和 progress。 读文件、打印日志、重复运行命令是 activity；写出候选、验证候选、通过 verifier 才能改变 completion readiness。

信号 触发后下一步 边界
analysis_progress 本地路由 cheap_execute，要求把已验证事实转成命令、验证或交付。 它是 inferred 事件，只能作为控制信号，不能伪装成 verifier 通过。
replan_hypothesis 进入 hypothesis_apply，只验证/应用当前假设，避免重新宽泛探索。 如果 apply 被 length 截断，只给一次 premium recovery。
delivery_candidate_needs_delivery 本地路由 cheap_execute，要求把已有候选写到交付目标或做一个窄验证。 连续提醒不落地会变成 delivery_candidate_floor_exhausted，再升级一次 recovery。
execution_stall 连续 stall 后路由 premium_recover，要求恢复非交互式短命令。 它描述执行通道卡住，不等于模型能力不足。
completion_readiness delivery/test/verifier 证据足够时进入 premium assessment 或 final guardrail。 finish_reason=stop 不是完成；最终完成必须来自交付和 verifier/outcome。

现在可以接受什么

可以接受

  • safe-control 子里程碑可以算完成。
  • Budgeted Route Action 的 plumbing 已经验证。
  • Episode/Event 最小 runtime 能影响路由，并能被 trace/replay 审计。
  • shadow-relay 上 outcome-aware online control screening 通过。

还不能接受

  • 不能因为单条 canary 就说策略泛化。
  • analysis_progress 仍是 inferred，需要更多任务验证误报率。
  • native tool event hook 还没有接到 agent runtime。
  • 还没有每任务 3 次以上的 acceptance 数据。

工程经验

  1. finish_reason=stop 只能说明一次响应结束，不能当成任务完成。
  2. activity 和 progress 必须分开。读文件、搜索、打印更多日志不应该清空 no-progress 压力。
  3. 路由成本要按整条 trajectory 算，不按单次调用价格算。
  4. 本地规则只能处理高置信动作；实现、恢复、隐藏测试 gap 仍需要 semantic 或 premium reasoning。
  5. 强模型应该买“方向改变”和“关键收尾”，不应该买越来越长的原地续写。
  6. 每个状态 floor 都要有退出条件，否则很快变成另一种死循环。
  7. 离线 replay 可以筛掉坏策略，但不能替代真实 benchmark。

下一步

接下来不应该继续围绕 shadow-relay 调阈值。更有价值的工作是把同一套状态控制拿去跑 holdout： 选一个短数据/算法任务，保持任务名无特例，先做 1 次 screening；如果不回退，再按每任务至少 3 次做 acceptance。
