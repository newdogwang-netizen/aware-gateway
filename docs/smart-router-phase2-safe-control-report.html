第二阶段：把 smart-router 从 prompt 判断推进到控制系统

第一阶段证明了 prompt-based router 能跑通，也留下了一个清楚的问题： 每次 agent 请求都问 Decision Model，会带来固定成本、固定延迟和新的故障面。 第二阶段不改 agent planner，只在网关层做一件事：用可观测证据判断本次调用最低需要哪一档模型能力。

Issue #1 到底要解决什么

Issue #1 的方向可以浓缩成一句话：把 smart-router 从每轮独立 prompt 判断，演进成 事件驱动的任务状态控制器。它不替 agent 做计划，也不宣布任务完成； 它只根据当前证据，判断这一次模型调用最低需要 cheap 还是 premium。

第一阶段的发现给了它出发点：成本不是由单次模型价格决定，而是由完整 agent trajectory 决定。 如果 cheap model 在错误路径上多走十步，总成本未必低；如果 premium 用在关键假设和收尾，反而可能更便宜。 

Session: 请求发生在哪里
Episode: 当前在解决什么
Event: 实际发生了什么
State: 基于证据，现在知道什么
Policy: 当前状态最低需要哪档能力
Decision: 本次为什么选择这个模型
Outcome: 这条路径最后有没有产生有效交付

现在完成到哪里

真正想要的网关不是一组更聪明的关键词规则，而是知道当前处于哪条任务线、已经发生了什么、 下一步最低需要何种能力，并能从最终交付反向验证策略。按这个标准看，Safe Control 只是其中一个子里程碑。

模块 状态 含义
Prompt Router 已完成 能根据当前请求和短期摘要，在 Flash 与 Opus 之间做语义选择。
Safe-control Rule Layer 已完成 确定性动作不再每次付 semantic judge 成本，并且有连续 cheap 探测上限。
Session-level Stateful Heuristics 已完成 同一 trial 内保留最近决策摘要、重复错误指纹、premium cooldown 等轻量状态。
Event-driven State Controller 未完成 还没有把文件读取、修改、测试、错误和 verifier 结果统一投影成状态。
Episode Runtime 未完成 还不能稳定识别当前 agent 正在解决哪条任务线、哪条假设、哪个阶段。
Budgeted Route Action 第一版已验证 A4 真实 pilot 通过；但截断率偏高，profile 还需要 outcome 校准。
Delivery Feedback 未完成 还没有把一次路由选择和最终交付质量、测试结果、成本路径稳定关联起来。
Offline Policy Evolution 未完成 还没有用多任务 outcome 数据反向更新策略，只是在人工复盘中调整。

所以验收边界很窄：Phase 2 Safe Control 子里程碑可以标记完成；Issue #1 的总体目标必须保持 open。 后续不宜继续添加更多关键词规则；Budgeted Route Action 第一版已经接上，下一步进入最小 Episode/Event 模型。

第二阶段先抓哪个主要矛盾

完整的 Episode Resolver、Event Store 和 Delivery Feedback 都值得做，但一次全做会把实验拖散。 Phase 2 先抓一个最直接的矛盾：很多请求只是读文件、搜索、跑已有测试、按固定格式回答， 却仍然要付一次 semantic judge 的成本。

本地规则接管

文件读取、搜索、已有测试执行、普通固定格式输出，直接路由到 cheap model。

同一错误重复出现、核心假设被反证、最终完成确认，直接升级到 premium model。

语义 judge 保留

实现、调试、架构、多文件修改、错误恢复等模糊场景，仍交给原来的 prompt router。

本地规则只处理高置信动作。证据不足时，不强行降级。

实验链路

真实 benchmark trial 仍走 aware-gateway。差别在于 smart-router 前面多了一层保守的 safe-control。

验证一：先用 probe 排除控制面幻觉

真实模型实验很贵，所以先做一个确定性 probe。它启动 mock provider、mock decision endpoint 和真实 gateway binary。 这样不花真实 LLM 成本，也能验证 router、audit trace、规则命中和分析脚本是否一致。

场景 预期 结果
读文件、搜索、跑已有测试、固定格式输出 safe-control 直接 cheap 通过
同一错误重复、假设被反证 safe-control 直接 premium 通过
连续 premium 后冷却、最终完成确认、模糊实现请求 分别进入 cooldown、guardrail、semantic judge 通过

Probe 汇总：9 个场景全部命中预期；9 条 agent trace；2 条 decision trace；6 条 safe-control； 1 条 completion guardrail。mock 成本只用于检查计费链路，不当作经济结论。

实验暴露的问题和修复

第二阶段没有只保留好看的 run。A1 证明方向可行，A2 暴露控制边界和 provider 归因问题， A3 验证修复后质量仍可通过，同时暴露新的时间和预算问题。A4 接上预算控制后继续通过， 但也暴露了 profile 过紧会把任务切成更多小步。

目前能下什么结论

  1. safe-control 可以减少不必要的 semantic judge 调用，但它不是自动省钱机器。
  2. shadow-relay 上 A1、A3、A4 都通过，成本分别是 $2.2468、$3.7369、$3.4808。
  3. A2 说明本地 cheap 规则必须有连续上限，否则会把早期方向判断推迟太久。
  4. A3 说明质量可以保住，但下一层瓶颈变成 route action 的预算和停止条件。
  5. 现在完成的是“减少每轮 judge”的实验目标，还没有完成“状态化智能决策层”的架构目标。
  6. Budgeted Route Action A4 没有伤害质量，但 profile 过紧会增加碎片化迭代。

这还不是泛化结论。现在只有一个任务上的三条通过样本和一条 provider incomplete 样本。 至少覆盖 5 到 10 个不同任务类型后，才适合判断它是否真的提高了智能决策水平。

下一步

第二阶段后半段应该继续沿着 Issue #1 走，但不要一次性做完所有抽象。 还差三根主梁：Episode Runtime 负责识别任务线，Event Projection 负责记录已经发生了什么， Outcome Loop 负责用最终交付反向验证策略。预算控制面已经接上并通过一条真实 pilot， 下一步要让 profile 接入 Episode/Event 信号，而不是继续手工加规则。 

1. Budgeted route action
   cheap_probe: smaller max_tokens, shorter timeout
   premium_recover: larger budget, guarded cooldown
   semantic judge: choose model plus budget

2. Episode event projection
   file_read, file_modified, test_failed, test_passed, verifier_result

3. Delivery feedback
   route decision -> file change -> test/verifier outcome
